## The canonical contract

[`../../shared/api/API_CONTRACT.json`](../../shared/api/API_CONTRACT.json) is
the machine-readable source of truth for every route, generated by this
audit from the live account + Lambda source + `docs/api-samples/`. Flutter
and React models should both be generated/reviewed against it, not against
each other's code, so they can't silently drift.

**Reconciliation note:** the existing `API_REFERENCE.md` states "14 frozen +
23 legacy = 37 routes." The live account and `deploy/routes.py` source both
show **15 frozen-contract + 20 legacy = 35 declared routes**, plus **2
undeclared live routes**:
- `OPTIONS /{proxy+}` — an API-Gateway-internal CORS catch-all, not a content route, harmless.
- `POST /score/refresh` — **a genuine, undocumented, orphaned live route.** It targets
  the retired `rakshak-score-refresh` Lambda, still returns a valid (differently-shaped)
  response, and is in neither `deploy/routes.py`, `AWS_RESOURCES.md`, nor `API_REFERENCE.md`.
  Verified live during this audit (see the Output Summary at the end of this
  document, and `API_CONTRACT.json`'s `undocumented_live_routes`). **Do not build
  against it** — its `safe_score` field is a 0..1 fraction, unlike every other
  route's 0..100 `safetyScore`/`safety_score`.

## API client architecture (one shared layer, described — not implemented)

Every current app already has a config/service layer pointed at the same
base URL:

- `dashboard/src/config/api.js` — `fetch()`-based, `ENDPOINTS` map of legacy paths.
- `dashboard/src/hooks/use*.js` — polling hooks, each owning one endpoint's lifecycle.
- `apps/citizen-web/src/services/api.js`, `apps/police-web/src/services/api.js` — `axios`-based, each with a `try/catch` fallback from a contract path to a legacy path.
- `citizen-app/lib/services/api_service.dart`, `police-app/lib/services/api_service.dart` — `dio`-based (not read in full this pass; same base URL confirmed via `.env.example`).

**Recommendation: standardize on the contract paths going forward, keep the
legacy-path fallback pattern already in `apps/*/src/services/api.js` since
both path families point at the same handler for every route that has a
contract equivalent** (verified live-identical for `/patrols` ↔
`/dashboard/patrols` and `/heatmap/live` ↔ `/dashboard/heatmap` this audit).
For routes with no contract equivalent (most of the legacy list —
`/sos/live`, `/sos/cancelled`, `/police/route`, `/reports/*`,
`/citizens/ping`, `/police/citizens/active`, `/patrol/optimize`,
`/patrols/{id}/status`), there is nothing to migrate to; keep calling them
as-is.

Proposed shared layer (**description only — this audit does not write
frontend code**):

```
shared/api/
  API_CONTRACT.json     # canonical route/schema source (this audit's output)
  api_client.ts          # thin fetch/axios wrapper: base URL, timeout (8s,
                          # matching every existing client), JSON parse,
                          # {error} extraction on non-2xx
  api_client.dart        # dio-based equivalent for citizen-app/police-app
  endpoints.ts            # typed endpoint URL builders, one function per
                          # API_CONTRACT.json route, contract path preferred
  endpoints.dart          # same, Dart
  polling_service.ts      # generic "poll every Nms, retry with backoff,
                          # keep last-known value on error" hook factory —
                          # replaces the 5 near-identical copies of this
                          # logic in dashboard/src/hooks/use*.js
  polling_service.dart    # Riverpod StreamProvider/Timer equivalent
```

`api_client.*` and `endpoints.*` responsibilities: own the base URL and
per-request timeout, never own polling cadence or retry policy (that's
`polling_service.*`) or UI state (that's the screen/hook). This separation
doesn't exist yet in any of the three current web apps — `dashboard`'s hooks
each hand-roll their own `fetch` + `setInterval`. Unifying it is a
recommendation, not a requirement for correctness; the current
duplication works.

## State management recommendation

**Flutter (citizen-app, police-app): keep Riverpod.** Both apps already
declare `flutter_riverpod: ^2.5.1` in `pubspec.yaml` under an explicit
`# State Management` comment — this was already decided by whoever scaffolded
these apps. No reason to introduce Provider or Bloc alongside it.

**React (dashboard, apps/citizen-web, apps/police-web): Context API + custom
hooks, not Redux or Zustand.** Evidence: none of the three `package.json`
files declare any state-management library — `dashboard/src/hooks/*.js`
already implements the pattern with plain `useState`/`useRef`/`useEffect`,
one hook per backend resource (`useSnapshot`, `useLivePatrols`,
`useActiveIncidents`, `useRiskData`, `useTimeline`). This works today because
each screen mostly owns its own polled data with little cross-screen sharing.
Reach for Zustand only if `apps/citizen-web` or `apps/police-web` grows a
genuine cross-screen state need (e.g., an in-progress SOS that must be visible
from both a map screen and a status bar) that prop-drilling or a single
top-level Context can't handle cleanly — don't add it preemptively.

## What's new from this audit (mismatches — see also `API_CONTRACT.json`)

1. `POST /score/refresh` — live, undocumented, orphaned route (above).
2. Route-count discrepancy in `API_REFERENCE.md` prose (14+23=37 stated vs. 15+20=35 declared + 2 undeclared = 37 actual) — not fixed in that file by this audit (read-only scope); recorded here and in `API_CONTRACT.json`.
3. `GET /prediction/{zone}` (and its legacy alias, and `POST /predict`) return **camelCase** (`safetyScore`, `riskLevel`); `GET /dashboard/heatmap`/`/dashboard/snapshot` return **snake_case** (`safety_score`, `risk_level`) for the same underlying model score. Confirmed at the source level (`rakshak-dashboard/lambda_function.py`): `_prediction()` returns `rc.predict_safety()`'s raw camelCase dict; `_zone_scores()` (used by heatmap/snapshot) explicitly re-maps to snake_case. This is permanent, not a bug to fix — document it, don't paper over it with a client-side rename that then drifts.
4. `DATABASE_SCHEMA.md` describes a timeline event as `{type, message, timestamp, patrol_id}`; the live shape (confirmed via `docs/api-samples/` and `rakshak_common.make_event()`) is `{type, ts, detail, patrol_id?, pincode?}`. Use `ts`/`detail` — see `API_MODELS.md`.
5. `rakshak-score-refresh` is 1024MB live vs. 512MB documented in `AWS_RESOURCES.md`; 9 CloudWatch alarms exist live vs. 7 documented (2 extra are leftover alarms on the orphaned `sos-feed`/`score-refresh` functions). Neither affects the frontend contract; noted for completeness.

None of the above required a backend code change — every mismatch is a
documentation/consistency issue, not a broken contract.
